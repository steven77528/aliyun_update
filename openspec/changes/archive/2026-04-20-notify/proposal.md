# Proposal: 为 IP 变更引入 SMTP 邮件通知

## Why
- 当前流程在公网 IP 变化并成功更新阿里云安全组后，缺少面向相关人员的主动通知，导致变更可见性不足。
- 现有能力侧重失败告警，缺少“成功变更事件”通知链路，难以满足审计与运维协同需求。

## Scope (Current Release)
本期仅交付“SMTP 邮件通知”最小可用版本：

1. **变更事件通知（多目标汇总）**
   - 单次运行结束后按“运行批次”汇总发送 1 封邮件（或按账号汇总，二选一并固定）。
   - 汇总邮件必须包含每条目标记录的更新结果（成功/失败）与关键上下文。
   - 每条记录至少包含：变更时间、变更对象、旧 IP/新 IP、变更原因、执行结果、失败摘要（若失败）。

2. **配置化开关与收件人**
   - 提供通知总开关。
   - 提供 SMTP 连接配置与收件人地址配置。

3. **安全与脱敏基线**
   - 通知内容不得包含 `ACCESS_KEY_SECRET`、完整 `ACCESS_KEY_ID`、完整异常堆栈等敏感信息。
   - 通过白名单字段构建通知载荷，避免原始数据透传。

4. **失败监控衔接**
   - 邮件发送失败时记录结构化日志并触发现有告警链路（沿用当前失败告警机制）。
   - 邮件发送失败时最多重试 3 次（含首次发送共最多 4 次尝试，需在实现中固定语义并保持一致）。
   - 支持基础限频，避免邮件或告警风暴。

5. **执行日志步骤对齐**
   - 当本轮发生安全组配置修改（存在更新尝试）时，增加 `step4` 日志阶段，输出汇总通知发送结果。

6. **测试与文档**
   - 增加邮件通知核心路径测试（成功发送、发送失败、开关关闭）。
   - 补充配置说明与故障排查文档。

## Non-goals (Out of Scope for Current Release)
- 本期不实现 webhook/IM 新渠道扩展（后续迭代再做统一通知中心）。
- 本期不引入复杂模板引擎与多语言邮件模板。
- 本期不引入外部消息中间件。

## Success Criteria
满足以下条件即视为达成：

1. 多目标场景下，单次运行后会发送汇总邮件到配置收件人。
2. 汇总邮件中每条目标记录都明确标注更新结果（成功/失败）。
3. 当单条记录失败时，邮件中包含该条失败摘要，且不影响其他记录结果展示。
4. 当未发生任何变更且无失败时，可按配置选择不发送通知邮件。
5. 邮件正文包含时间、对象、旧/新 IP、原因、结果等关键信息。
6. 邮件与日志不泄露敏感凭证。
7. 邮件发送失败可被记录并可观测（触发失败告警或明确失败日志），并执行最多 3 次重试策略。
8. 当发生安全组配置修改时，日志中出现 `step4`，并输出通知发送结果（成功/失败、重试次数）。
9. 新增测试覆盖关键路径，文档可指导完成配置与排障。

## Risks / Open Questions
- SMTP 服务商差异（SSL/TLS/端口/认证方式）可能影响接入体验。
- 汇总粒度采用“全局单封”还是“按账号分组多封”需固定策略并保持可预期。
- 发送失败重试策略与现有告警限频策略的边界需明确，避免重复噪音。
