## Context

当前实现以单文件脚本为主（`src/ip_sync.py`），承担配置加载、IP 获取与比较、阿里云安全组规则更新、通知发送、日志输出等多个职责。该结构在功能扩展时容易引发以下问题：
- 变更影响面大，局部调整容易波及非目标逻辑；
- 测试边界不清晰，难以对关键行为进行模块级验证；
- 日志与通知等横切能力与业务流程耦合，阅读和排障成本高。

本次设计目标是在不改变现有业务语义与运行方式的前提下完成模块化拆分，并确保与现有日志规范、通知可读性规范保持兼容。

## Goals / Non-Goals

**Goals:**
- 将单文件职责拆分为独立模块：配置管理、IP 管理、安全组更新、通知、日志。
- 建立统一编排入口，明确模块调用顺序、输入输出与异常传播路径。
- 保持现有行为等价：更新触发条件、规则更新语义、通知触发时机、日志主流程结构不变。
- 明确幂等与事务边界：单次运行内以“目标规则”为最小处理单元，失败可记录并继续处理其余目标。

**Non-Goals:**
- 不引入新的外部依赖或消息中间件。
- 不改变配置文件业务语义与部署形态（仍兼容当前 Docker/脚本执行方式）。
- 不调整云侧安全组策略定义、不新增规则编排能力。

## Decisions

1. 模块边界采用“能力分层 + 单向依赖”
- 决策：按职责拆分为 `config_loader`、`ip_service`、`sg_service`、`notifier`、`log_service`，由 `main`/orchestrator 串联。
- 备选：继续在单文件内按函数分区。
- 选择理由：文件级边界更易控制依赖与测试范围，后续扩展（例如增加通知渠道）更可控。

2. 通过显式参数注入共享上下文，避免全局状态
- 决策：配置对象、logger、运行上下文（当前IP、目标列表）在模块调用时显式传递。
- 备选：使用模块级全局变量共享。
- 选择理由：显式注入可降低隐式耦合，便于单测替换依赖并验证边界行为。

3. 事务边界定义为“单目标规则更新”
- 决策：每个目标规则独立执行“读取旧值→判断变化→调用更新→记录结果”；单目标失败不回滚其他目标。
- 备选：整批规则作为单事务，任一失败即全局失败。
- 选择理由：符合当前批处理脚本特性与可用性要求，避免单点失败阻断全部更新。

4. 幂等策略保持“IP 未变化即跳过，变化才更新”
- 决策：`ip_service` 负责给出变化判定，`sg_service` 仅在变化时执行更新。
- 备选：由 `sg_service` 内部重复判断变化。
- 选择理由：职责清晰，减少重复逻辑，并与现有流程语义一致。

5. 异常处理采用“分层捕获 + 结构化结果汇总”
- 决策：模块内部捕获可恢复异常并返回标准化结果对象；不可恢复异常上抛给 orchestrator 统一收口。
- 备选：全部异常直接上抛，由顶层一次性处理。
- 选择理由：可在不中断整批处理的前提下保留失败细节，满足通知与日志可追溯要求。

6. 日志关键字段与输出模板保持兼容
- 决策：日志模块统一输出并保留关键字段（账号、区域、安全组、规则、旧IP、新IP、结果、失败原因、耗时）。
- 备选：各模块自行打印日志。
- 选择理由：集中治理可保证格式一致性，持续满足 `log-standardization` 约束。

7. 配置策略：不新增必填项，新增项仅允许可选并给默认值
- 决策：优先复用现有配置结构；若为模块化引入内部配置开关，必须提供默认值并保持旧配置可运行。
- 备选：一次性引入大量新配置并要求迁移。
- 选择理由：降低迁移成本与发布风险，保持环境差异最小化。

## Risks / Trade-offs

- [风险] 拆分过程中行为漂移（更新条件、通知时机变化）  
  → 缓解：建立行为等价验收清单，按“有变化/无变化/部分失败”三类场景回归验证。

- [风险] 模块拆分后依赖方向失控，出现循环引用  
  → 缓解：强制单向依赖（orchestrator → service；service 间禁止横向调用）。

- [风险] 日志文案调整影响历史检索脚本  
  → 缓解：保留核心步骤与关键字段，新增信息采用向后兼容方式追加。

- [权衡] 增加模块文件会提高初期结构复杂度  
  → 缓解：通过统一编排入口与模块职责文档降低理解成本。

- [风险] 目标规则逐条处理时，部分成功可能带来运维认知成本  
  → 缓解：通知中明确成功/失败统计及失败明细，便于后续人工补偿。

## Migration Plan

1. 建立模块骨架与统一编排入口，保持旧入口可对照执行。
2. 按“配置→IP→安全组→通知→日志”顺序迁移逻辑，每迁移一层即进行等价回归。
3. 将现有测试按模块边界重组，并补充端到端等价场景。
4. 灰度期保留可比对日志，确认结果一致后切换到模块化入口。
5. 回滚策略：若出现不可接受偏差，切回旧单文件入口并保留现场日志用于定位。

## Open Questions

- 是否需要在本次变更内引入统一结果数据结构（例如 `UpdateRecord`）作为通知与日志的共享契约？
- 是否要求在模块化后继续保留完全一致的日志文案，还是仅要求关键字段与语义一致？
- 现有测试覆盖率是否足以支撑“行为等价”判断，是否需要先补一轮基线测试？
