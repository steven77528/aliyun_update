## Context

当前通知能力已覆盖“邮件中展示规则可读名称”，但尚未规范完整邮件版式、失败明细可视化以及发送时序策略。需求来源于 [`openspec/requitement/format-mail.md`](openspec/requitement/format-mail.md:1)，其核心约束包括：固定主题、结构化正文、失败记录表格（含字段映射与“修改时间”列）、1.5 倍行距，以及夜间延迟发送与 2 小时限频并存。

该变更属于跨模块设计：
- 内容渲染层：负责主题、段落、表格、样式输出。
- 数据映射层：负责从运行记录与 `aliyun.yaml` 组装邮件行数据。
- 调度层：负责时间窗口与限频策略。

## Goals / Non-Goals

**Goals:**
- 定义统一且可验证的邮件正文结构，确保“生成时间/IP/统计/失败详情”完整可读。
- 定义失败明细表格字段来源和展示规则，避免实现口径分歧。
- 定义夜间延迟（22:00-07:00）与 2 小时限频的组合行为。
- 保证邮件正文第二行“生成时间”为邮件实际发送时间；失败明细中的“修改时间”为记录实际修改时间。

**Non-Goals:**
- 不引入邮件以外的新通知渠道（短信、IM、Webhook）。
- 不更改安全组规则更新业务语义，仅调整通知表达与发送时序。
- 不规定具体 HTML/CSS 库或 SMTP 客户端实现细节。

## Decisions

1. 邮件模板采用“固定骨架 + 动态数据填充”
- 决策：主题与前五行文本结构固定（第二行为“生成时间”），失败明细按记录动态扩展。
- 原因：固定骨架便于验收与回归；动态明细满足不同批次规模。
- 备选：纯自由文本拼接。未采用，因为难以保证字段完整性和一致性。

2. 失败明细表按“记录粒度”渲染
- 决策：每条记录输出一行，列为序号、修改时间、账号、区域、安全组、规则、旧IP、新IP、结果、失败原因。
- 原因：与原始处理记录一一对应，便于定位与追溯。
- 备选：仅按账号或区域聚合。未采用，因为会损失排障细节。

3. 安全组/规则单元格采用双行展示
- 决策：第一行展示 alias/name，第二行展示 ID。
- 原因：同时满足可读性（人看名称）与可定位性（系统 ID）。
- 备选：仅展示名称或仅展示 ID。未采用，因为信息不完整。

4. 调度策略采用“夜间缓冲 + 白天限频窗口”
- 决策：
  - 22:00-07:00 期间产生的更新进入缓冲队列；
  - 次日 07:00 触发统一发送；
  - 白天发送仍受“每 2 小时最多一次”约束。
- 原因：降低夜间邮件打扰，同时维持既有限频策略。
- 备选：夜间实时发送或完全跳过夜间。未采用，分别会增加打扰或丢失及时通知。

## Risks / Trade-offs

- [风险] 夜间缓冲与 2 小时限频重叠，可能导致 07:00 批次与 07:xx 普通批次冲突  
  → 缓解：规定 07:00 统一发送成功后刷新限频时间戳，后续按窗口计算。

- [风险] 不同邮件客户端对表格样式支持差异，居中与行距可能表现不一致  
  → 缓解：使用兼容性较高的内联样式并提供最小可读降级。

- [权衡] 固定模板提高一致性，但灵活性降低  
  → 缓解：将字段映射与模板结构解耦，后续可通过配置迭代文本。

- [权衡] 明细粒度完整会拉长邮件正文  
  → 缓解：失败详情表展示失败记录；夜间多次修改统一发送时确保记录完整并控制样式冗余。

## Migration Plan

1. 先在规范层落地邮件结构与发送时序的 MUST 约束。
2. 基于规范更新通知渲染逻辑与调度逻辑（后续 `/opsx:apply` 执行）。
3. 增加覆盖场景：白天发送、夜间缓冲、07:00 统一发送、失败详情为空/非空。
4. 发布后观察邮件发送频率与失败原因展示完整度，必要时追加迭代变更。

## Open Questions

- 当夜间失败记录很多时，是否需要增加表格行数上限与附件/链接降级策略。
- “统计信息”中的总数是否仅统计本次邮件覆盖窗口内记录（建议是）。
- 若 07:00 发送失败，是否立即重试或等待下一次 2 小时窗口。
