# Proposal: format-config-and-logging（按当前 requirements 对齐）

## Why
- 需求已经明确提出配置、日志、目录、Docker 交付四类标准化目标，但缺少统一提案会导致实现口径不一致。
- 在多账号、多安全组、多规则场景下，仅用规则 ID 可读性不足，需通过规则 `name/alias` 提升日志与邮件可定位性。
- 需要把“阿里云配置采用 YAML（含示例结构）”这一关键要求固定到工件，避免后续偏离。

## Scope (Current Release)
1. **配置分层与格式约束**
   - 配置分三部分：基础配置、阿里云配置、通知配置。
   - 阿里云配置采用 YAML，支持层级：`accounts[] -> security_groups[] -> rules[]`。
   - 阿里云配置包含账号别名、安全组别名、规则别名（或规则名称）用于日志展示。
   - 通知配置包含 SMTP 相关参数；基础配置与通知配置可使用 JSON。

2. **规则可读性增强**
   - 规则 `name/alias` 在 step3 更新日志中展示。
   - 规则 `name/alias` 在通知邮件中展示，便于快速定位问题。

3. **日志格式标准化**
   - 执行日志按固定模板输出：开始边界、step1、step2、step3、step4、结束边界。
   - 日志按天落盘，命名 `ip_sync_YYYYMMDD.log`。
   - 日志默认保留 7 天，超期自动清理。
   - 禁止输出敏感信息、过细调试信息、冗长异常堆栈。

4. **目录与交付标准化**
   - 目录目标：脚本在 `src/`，测试在 `tests/`，最终产物在 `target/`。
   - 提供 `Dockerfile` 与 `docker-compose.yml`。
   - 交付包含镜像压缩包，并定义 `config/`、`data/`、`logs/` 挂载目录。
   - 提供完整构建与运行文档。

## Non-goals
- 本期不新增除邮件外的其他通知渠道。
- 本期不扩展外部日志平台或复杂可观测栈。
- 本期不改动核心业务目标（IP 变化触发规则更新）的语义。

## Success Criteria
1. 配置分层能力满足三段模型，且阿里云 YAML 配置支持多账号/多安全组/多规则。
2. 规则 `name/alias` 在日志与通知邮件均可见。
3. 日志模板严格覆盖 step1~step4 与开始/结束边界。
4. 日志文件命名和 7 天保留策略生效。
5. 日志不泄露密钥、密码等敏感信息。
6. 目录规范和 Docker 交付要求可执行（含镜像包与挂载目录）。
7. 文档可指导用户完成部署、配置与运行。

## Risks / Open Questions
- 规则字段命名采用 `name` 还是 `alias` 需要在设计中固定映射规则。
- 阿里云 YAML 与基础/通知 JSON 的加载顺序、合并策略与报错体验需明确。
- `tests/` 与现有目录布局的迁移成本需要在任务中显式安排。
