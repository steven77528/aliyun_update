## Context

现有实现将“云账号 + 安全组规则”抽象为单一阿里云模型，并在 step3 中逐条调用阿里云 SDK 修改安全组规则来源 CIDR。华为云能力接入后，需要在尽量少破坏现有结构的前提下完成：

- 多云统一配置解析
- 按云厂商路由更新逻辑
- 日志和通知展示云厂商信息

同时，华为云 VPC 规则更新流程与阿里云不同。现有调研结论是华为云没有直接对应“按规则 ID 修改来源 IP”的稳定实现入口，因此采用替换式流程更稳妥：先查询原规则，按新 IP 创建等价规则，再删除旧规则。

## Goals / Non-Goals

- Goals
  - 支持阿里云与华为云目标规则在同一轮处理中并行更新
  - 保持现有阿里云行为与测试语义稳定
  - 配置结构可扩展到更多云厂商
  - 日志与通知中能区分云厂商
- Non-Goals
  - 不处理除阿里云、华为云外的其他厂商
  - 不引入新的调度模型，仍沿用当前单轮/循环执行模式
  - 不在本次中重做 step3 全量日志格式，仅在现有基础上增加云厂商字段

## Decisions

1. 统一配置文件命名与结构
- 决策：新增 `cloud.yaml` 作为推荐配置入口，顶层支持 `aliyun:` 与 `huawei:` 两个并列字段。
- 兼容：保留 `ALIYUN_CONFIG_FILE` 的兼容路径；若文件根节点仍是旧的 `accounts:` 结构，则按阿里云旧格式解析。

2. 模型层增加云厂商标识
- 决策：在账号与目标模型中增加 `provider` 字段。
- 原因：主流程、日志、通知都需要在不分叉大量逻辑的前提下区分云厂商。

3. 更新服务按 provider 分派
- 决策：将现有 `AliyunRuleUpdater` 泛化为多云更新入口，根据 `provider` 选择具体 updater。
- 原因：主流程仍然只关心“给定目标，是否更新成功”，避免编排层出现大段厂商分支。

4. 华为云采用“查询 + 新建 + 删除”的规则替换流程
- 决策：基于华为云 SDK 查询当前安全组和规则详情，复制除来源 IP 外的关键字段，创建新规则后删除旧规则。
- 风险：若创建成功、删除失败，会产生重复规则。
- 缓解：将该场景明确记录为失败并保留错误原因，便于人工清理；不在未确认新规则创建成功前删除旧规则。

5. 通知与日志增加 provider 字段
- 决策：通知明细新增“云厂商”列；step3 结构化日志与通知项中新增 `provider` 字段。
- 原因：多云并行后，单靠账号/区域不足以快速判断规则所属云厂商。

## Risks / Trade-offs

- 风险：华为云规则字段复制不完整可能导致新建规则与旧规则语义不一致。
  - 缓解：优先复制方向、ethertype、协议、端口范围、描述、远端地址等关键字段；测试覆盖请求体构造。
- 风险：统一配置文件上线后，用户仍可能继续使用 `aliyun.yaml`。
  - 缓解：继续兼容旧环境变量和旧格式 YAML；README 中明确新旧差异。
- 风险：通知表头变更可能影响依赖固定格式的下游解析。
  - 缓解：仅新增“云厂商”列，其余字段顺序尽量保持稳定。
