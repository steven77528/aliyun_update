## Context

当前 step3 日志已经覆盖“更新/跳过”结果，但在多目标场景下缺少统一的目标标识行，用户无法快速从日志中定位具体账号、区域、安全组与规则。需求要求在 step3 中引入 `step3.n` 子步骤日志，并展示可读名称（alias/name）。

## Goals / Non-Goals

**Goals:**
- 为每个目标规则输出标准化 step3 子步骤日志（`step3.1`、`step3.2`...）。
- 在子步骤日志中统一输出：`${account} | ${region_id} | ${security_group_name} | ${security_rule_name}`。
- 在“变化更新”与“未变化跳过”两种分支都保留结构化结果日志，便于检索与比对。

**Non-Goals:**
- 不改变日志框架与落盘策略（文件命名、保留天数）。
- 不改变规则更新业务逻辑和重试策略。
- 不引入新的日志采集/可观测平台。

## Decisions

1. 采用“每目标一条 step3.n 定位日志”
- 决策：进入每个 target 处理前先输出 `step3.n：目标安全组：...`。
- 原因：该行天然作为后续结果日志的上下文锚点，便于 grep 与人工阅读。

2. 子步骤序号按遍历顺序递增
- 决策：序号从 1 开始，对每个处理目标递增（无论后续更新或跳过）。
- 原因：保证日志阅读时顺序稳定，避免仅对“发生变化”目标编号导致混乱。

3. 可读名称与 ID 同时保留
- 决策：step3.n 行使用可读名称；原有结果行继续保留 ID 信息。
- 原因：可读性与可定位性兼得，兼容现有排障习惯。

## Risks / Trade-offs

- [风险] 历史日志解析脚本可能依赖旧文案  
  → 缓解：保留原有关键结果日志，仅新增 step3.n 定位行。

- [风险] 目标很多时 step3 日志量增加  
  → 缓解：仅增加一条简洁定位行，不引入额外冗余字段。

- [权衡] 子步骤号是运行时顺序号，不是稳定业务主键  
  → 缓解：同一行同时携带账号/区域/安全组/规则可读信息以确保可回溯。
